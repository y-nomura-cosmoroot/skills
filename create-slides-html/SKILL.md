# reveal.js 高品質HTMLスライド作成スキル

reveal.js + Tailwind CSS(CDN) で、AIっぽさを消したHTMLスライドを作る。**全プロセス**を定義する。デザインに入る前に、必ずフェーズ0・1・2・2.5を完了すること。なぜなら、見た目のルールだけ整えても、コンテンツの設計と文章がAIっぽいままだと「機械が作った資料」に見えてしまうからだ。

成果物は原則として**単一のHTMLファイル**（reveal.js と Tailwind を CDN から読み込む）。`slide-template/` のようなビルド構成は理想形の参考であって、毎回そこまで作る必要はない。ユーザーが既存テンプレートやリポジトリを指定した場合だけ、その構成に合わせる。

---

## フェーズ0：参照デザインの検出とトークン抽出（最初に必ず実施）

スライド依頼を受けたら、**まず参照デザインが指定されているか**を確認する。

判定（いずれかに該当すれば参照ありとして扱う）:
- ユーザーが `.pptx` のパスを指定（「このpptxと同じデザインで」等）
- ユーザーが参照したいWebサイトのURLを指定（「このサイトと同じ雰囲気で」等）
- 会話中で既存資料・既存サイトを「同じ見た目で」「テンプレとして」と指示された

分岐:

**参照PPTXがある場合** → `create-design-md-from-pptx <pptxパス>` を実行して DESIGN.md を生成させ、読み込む。
**参照サイトがある場合** → `create-design-md <URL>` を実行して DESIGN.md を生成させ、読み込む。

参照ありの場合、生成された DESIGN.md の Color Palette / Typography / Components / Layout / Do's & Don'ts を、**フェーズ3のデフォルトデザインシステムの代わりに** Tailwind config（`c-` クラス・カラー定義）へ落とし込む。デフォルトの配色制約は参照元のパレットに置き換える。

**参照がない場合** → `references/designs.json` を読み込み、登録済みデザインの一覧（`name` / `sourcePptx` / `features`）をユーザーに提示する。AskUserQuestion で利用するデザインを選択してもらい、選ばれたエントリの `designMdPath`（`references/<design-name>/DESIGN.md`）をフェーズ3のデザインシステムとして読み込み、Color Palette / Typography / Components / Layout / Do's & Don'ts を Tailwind config（`c-` クラス・カラー定義）へ落とし込む。以降のスライドはすべて、選ばれた DESIGN.md を基準にデザインを統一する。

`designs.json` には各デザインの `name`（フォルダ名）、`sourcePptx`（もとパワポ名）、`designMdPath`（DESIGN.md の相対パス）、`features`（特徴の説明文）が配列で並ぶ。新しいデザインを追加するときは `references/design-N/` フォルダと DESIGN.md を作り、`designs.json` の `designs` 配列にエントリを追記する。

重要：参照が与えられているのにデフォルトのデザインで作らないこと。ただし**フェーズ1・2・2.5はどちらのケースでも必ず実施する**。これらはコンテンツ設計のフェーズで、見た目とは独立している。

## フェーズ1：ヒアリング（スライド着手前に必ず実施）

すでに会話で明示されている項目はスキップしてよい。不足していれば確認する。

① **読み手は誰か** — 役職・立場、前提知識レベル、意思決定権の有無
② **このスライドで達成したいこと** — 読み手に何をしてほしいか（承認・理解・行動）、成功の定義
③ **全体の結論（So What）** — 全部見た後に残るべき1文。未定なら一緒に言語化する
④ **情報の流れ** — 結論先行（PREP）か、課題から始める順か

## フェーズ2：レポート作成と確認（スライド変換前のゲート）

ヒアリング完了後、スライドを作る前にレポート形式で内容を整理し、ユーザーに確認を求める。

```
# [タイトル]

## 対象読者と目的
- 読み手：[役職・前提知識]
- 達成すること：[具体的なゴール]
- 取ってほしいアクション：[承認・理解・行動など]

## 全体結論（エグゼクティブサマリー）
[全部見た後に残すべき1〜3文]

## 構成（起承転結）
### 起：前提・背景
### 承：現状・課題
### 転：示唆・分析
### 結：結論・提言・次のアクション

## スライド構成案（目次）
1. [スライドタイトルとメッセージライン案]
2. ...

## 懸念点・要確認事項
- [不足データやユーザー確認が必要な点]
```

提示後、必ず確認する：「上記の内容・構成でよろしいですか？修正があればお知らせください。承認いただけたらスライド作成に進みます。」 ユーザーの承認なしにスライド作成へ進まない。

## フェーズ2.5：テキストのAI臭除去（スライド変換前に必ず実施）

レポート承認後、スライドに載せるテキストを書き直す。文章からAIっぽさを消すことで、人が作ったスライドに仕上がる。

- **カギ括弧の多用を禁止** — 強調や定義で囲まず文脈に溶かす。固有名詞や引用など本当に必要なときだけ最小限に。
  NG「考える工程」と「形にする工程」を分ける → OK 考える作業と形にする作業を分ける
- **丸括弧で補足を逃がさない** — 括弧に入れるほどの説明なら本文に組み込む。不要なら削る。
  NG ターゲット（誰に見せるのか）が不明確 → OK 誰に見せるのかが不明確
- **コロン＋ラベル列挙を避ける** — 表の列ヘッダー等を除き、コロンでラベルを並べない。
- **テンプレ的な見出しを使わない** — 「3つの共通課題がある」「最適解である」を避け、具体的な動詞で言い切る。
- **抽象語だけで押し切らない** — 「重要」「効果的」「最適」「本質」だけで済ませず、何がどうなるかを動詞で書く。
- **定型の締め文句を入れない** — 「お気軽にお声がけください」「参考になれば幸いです」は使わない。
- **同義語の言い換え連打をしない** — 重要・大切・欠かせない、と繰り返さず1回で言い切る。
- **文のリズムを均一にしない** — メッセージラインが全スライド同じ構文にならないよう変化をつける。同じ型が3枚以上続かないように。

手順：承認レポートのテキストを上記で書き直し、カギ括弧の数を数え、メッセージラインを通しで読んでテンプレ感や同じ構文の連続がないか確認する。

## フェーズ3：reveal.js + Tailwind デザインシステム（承認後に適用）

> 参照PPTX/サイトから DESIGN.md を抽出した場合は、色・フォント・コンポーネントの値をその DESIGN.md で読み替える。以下の配色・フォントは**参照なしのデフォルト**で、`references/design.md`（Howard由来のデザインシステム）に準拠する。フラット・角丸なし・影なしなどの装飾ルール（§3-6）も**デフォルト時の話**で、選んだ DESIGN.md が角丸・ソフトシャドウ・Hero/CTAのグラデ等を定義しているなら、そのデザインの指定を優先する。

実装の構造ルールとサンプルは `references/structure.md`、デフォルトのデザイントークン（配色・フォント・コンポーネント）は `references/design.md` に詳細がある。**スライドのHTMLを書く前に、必ず `references/structure.md` と `references/design.md` を読むこと。** ここでは要点だけ示す。

### 3-1. 出力形式

- 単一HTMLファイル。reveal.js と Tailwind は CDN から読み込む（`assets/base.html` を雛形として使う）。
- Tailwind の設定（カラー・フォント・`c-` カスタムクラス）は HTML 内の `tailwind.config` に書く。`references/structure.md` の `lib/tailwind/config.js` 相当をインラインで持つ。

### 3-2. 構造ルール（厳守。理由とともに守る）

- **日本語で記述する。**
- HTML構造は `.slides > section > section` のように **section を入れ子**にする（縦方向のスライドグループ）。
- **全 `<section>` の直下に r-stretch ラッパー**を置く。上ぞろえは `class="r-stretch grid"`、中央ぞろえは `class="r-stretch grid place-items-center"`。r-stretch は reveal.js が高さを伸縮させる仕組みで、これに乗せないと縦位置が崩れる。
- `<section>` に `padding` や `margin` を**つけない**。余白はラッパー側で取る。section に余白を付けると reveal.js のスケーリングと干渉する。
- **r-stretch と同じ要素に `gap` をつけない**。gap は子要素の高さ計算を壊すため、内側にもう1段 div を噛ませてそこで gap を使う。
- カスタムクラスは **`c-` プレフィックス**。定義は Tailwind config（HTML内の `tailwind.config` のインライン、構成を作る場合は `lib/tailwind/config.js`）にまとめる。
- **カラーコードを原則使わない**。`#3D698F` などを直書きせず、Tailwind config で定義した色名（`bg-slate` 等）を使う。
- **`ul` `ol` `li` は禁止**。箇条書きや階層は `div` で組む。reveal.js のリスト見た目がAIっぽさの元になりやすいため。
- **絵文字はユーザーが要求したときだけ**使う。

### 3-3. デフォルトのカラーパレット（Howard由来。Tailwind config に定義）

| 役割 | 色名(config) | 値 | RGB |
|------|--------------|-----|-----|
| 背景・余白 | `bg` | `#FFFFFF` | 255,255,255 |
| カード淡灰 | `surface` | `#F2F2F2` | 242,242,242 |
| 見出し・本文インク | `ink` | `#44546A` | 68,84,106 |
| 補助テキスト | `sub` | `#999999` | 153,153,153 |
| 主アクセント（スレートブルー） | `slate` | `#3D698F` | 61,105,143 |
| ティールグレー | `tealgrey` | `#80A7A5` | 128,167,165 |
| セージグリーン | `sage` | `#ABBE92` | 171,190,146 |
| マウブ（限定） | `mauve` | `#775864` | 119,88,100 |

- グラデーションは**使わない**。背景・色面はすべてベタ塗り。表紙・セクション扉は `slate`（スレートブルー）一色＋白文字。
- 純黒 `#000000` のベタ使いは避け、インクは `#44546A`。差し色はスレートブルー＋セージ系に集約し、マウブ `#775864` は最小限。赤・橙・紫は使わない。

### 3-4. タイポグラフィ（Howard由来）

- 見出し・タイトル・数値は **Arial Bold（全大文字 / ALL CAPS）**、本文・リードは **Lato Light（サンセリフ）**。一部の小見出しに Poppins SemiBold を使ってもよい。和文フォールバックは游ゴシック系。
- 見出しと本文は同じサンセリフ系だが、**太字（Arial Bold）と細字（Lato Light）の対比**で階層を作る。セリフ体は使わない。
- セクション見出しは必ず全大文字。大きさの目安（`references/structure.md` の `c-` クラスに集約）：表紙タイトル 最大 → セクション見出し → 統計数値 → リード/本文。
- 本文色は `#44546A`、補助は `#999999`。詳細は `references/design.md` の Hierarchy 表を参照。

### 3-5. レイアウト原則

- **2系統を作り分ける** — 表紙・セクション扉は `bg-slate`（スレートブルー一色）＋白文字、本文スライドは白背景＋`#44546A` 見出し。
- **セクション見出し** — 各スライド上部に全大文字の太字見出し（Arial Bold）。
- **メッセージライン** — 全スライドに、そのスライドの結論を1文で言い切る見出し（断言形）。フェーズ2のメッセージライン案を使う。
- **階層は箇条書き記号を使わずロジックツリー型** — 第1階層（主論点、最大3）／第2階層（根拠、各3まで）／第3階層（補足）を `div` のインデントと文字サイズ・色で表現する。
- **統計・数値** — `surface`（淡灰）や `slate` の色面に Arial Bold の数値（色面上は白、白地はスレート）。
- **余白** — 広めに取り、1スライド1メッセージ。左揃えか中央揃えを統一。

### 3-6. 装飾ルール（禁止事項・デフォルト時）

デフォルト（Howard）ではフラットを守る。グラデーション背景、強い影・光彩・ベベル・3D、過剰なアニメーション、装飾的な囲み罫線、`・▶◆` などの装飾記号、絵文字（要求時を除く）は使わない。角丸はほぼ使わず（図解の円バッジを除く）矩形は直角。レイヤー差はベタ塗り色面の重なりで表す。統計カードに付ける淡い影（`0 2px 8px rgba(68,84,106,0.08)`）までは許容。**参照デザインを選んだ場合は、その DESIGN.md が角丸・ソフトシャドウ・限定的なグラデ（Hero/CTA等）を定義していればそれに従う**（この節はあくまでデフォルトの制約）。

### 3-7. グラフ・チャートは Chart.js を使う

**まず「グラフ」か「図解」かを切り分ける。** 数量そのもの（推移・構成比・比較・相関など、値に意味があるもの）はグラフ＝この節（Chart.js）。数量ではなく概念どうしの関係（包含・階層・流れ・循環など）は図解＝§3-8。同じ内容を両方で描かない。

棒・折れ線・円・ドーナツなどのグラフを載せるときは、**必ず Chart.js（CDN）で描く**。手書きのSVGや画像、CSSだけの擬似グラフは使わない。理由は、データを差し替えても体裁が崩れず、凡例や軸が自動で整い、後から保守しやすいから。

**データの形に合わせてグラフ種別を選ぶ**（見た目の好みで選ばない）。

| 見せたいこと | グラフ種別 | メモ |
|---|---|---|
| 1時点の構成比・割合 | 円 / ドーナツ | 要素は5つ程度まで。多いなら横棒に |
| 時系列の量の推移 | 縦棒（離散・年度）／折れ線（連続トレンド・複数系列） | 系列が多い推移は折れ線 |
| カテゴリ間の量の比較 | 縦棒（項目少）／横棒（項目多い・ラベル長い・順位） | ランキングは横棒 |
| 構成比の推移・内訳比較 | 積み上げ縦棒／100%積み上げ（各時点の割合を比較） | 実数か割合かで使い分け |
| 累積・面での推移 | エリア | 量の厚みを見せる |
| 期首→期末の増減要因 | ウォーターフォール | 何がどれだけ効いたか |
| 2変数の相関 | 散布図 | 分布・外れ値を見せる |

- データの系列色は**デザインシステムのパレットを使う**（デフォルトなら `#3D698F`(slate) / `#80A7A5`(tealgrey) / `#ABBE92`(sage)）。Chart.js の設定はJSなので色はHEXで書くが、これは config と同値で、本文HTML側のカラーコード直書き禁止の例外。
- 影・グラデ・3Dは付けない（フラットのまま）。装飾的なアニメーションは切る（`animation: false` 推奨）。
- グラフは1スライド1つを基本にし、上部にメッセージライン（断言形）、グラフ下や脇に出典・注釈を置く。
- canvas は高さを持つ `div` の中に置く（`r-stretch` 直下に裸の canvas を置かない）。実装の雛形は `references/structure.md` の「§8 Chart.js」を参照。

### 3-8. 図解（ダイアグラム）── 種類・意図・HTML/SVG実装

図解は数量ではなく**概念どうしの関係**を見せる。Chart.js では描けないので、**素の `div`（Tailwind）＋ SVG** で組む。以下は Slideland の図解分類「図解の種類、全部まとめてみた」（実物スライド例）を解析して、各図の意図・使いどころ・実装をまとめたもの。出典: https://x.com/slideland229/status/2018559165837574263 / https://www.slideland.tech/en/category-list

**手順を固定する。** ①文章から「示したい関係」を1つに絞る → ②下の一覧でその関係に合う型を選ぶ → ③その型の実装パターン（3-8-2）で組む → ④関係が薄いなら無理に図化せず箇条書きにする。型を先に決めて内容を後から流し込まない。関係に形が合っていない図（幅や色を変えただけ、意味のない横並び3カード）は図解ではない。

#### 3-8-1. 型の一覧（関係・意図・注意点）

各図の「注意点」は、その図がどんな失敗に陥りやすいか＝設計時に効かせる意図。

| 型 | 示す関係 | 意図・使いどころ | 陥りやすい失敗（注意） |
|---|---|---|---|
| ツリー / 組織図 | 分岐・階層・グループ化 | 階層構造を一目で示し、複雑な要素をグループにまとめる | 階層が深いほど場所を食い見づらい。大規模構造の丸載せは不向き |
| ピラミッド | 上下・優先度・土台↔頂点 | 頂点が最上位概念、下ほど土台。3層程度で構造を示す | 段ごとに幅・高さを変えたりgapを空けると全体が三角にならず崩れる（3-8-2参照） |
| フロー（横） | 順序・時系列・プロセス | 左→右の視線誘導で流れを追わせる。横長スライド向き | ステップを詰め込みすぎると矢印が渋滞 |
| フロー（縦） | 順序・段階（縦スクロール的） | STEP0→JOIN のように段階を上から下へ | 縦に長くなり1画面に収まりにくい |
| サイクル | 繰り返し・循環 | PDCAや改善・運用など終わりが始まりに戻るもの | 各ステップの役割は色分け・注釈で補う |
| ビフォーアフター | 変化の前後・対比 | AS-IS / TO-BE を左右または上下で対置 | 前後の対応関係を揃えないと比較にならない |
| 地図・マップ | 地理・拠点・エリア | 拠点や商圏を地図上のピン/点で示す | 引き出し線が増えて煩雑になりやすい（ベース素材が必要、後述） |
| パズル / ハニカム | 組み合わせ・噛み合い | 要素が組み合わさって全体が成り立つ | 形優先で中身が入りきらないことがある |
| 放射 | 中心からの発散・影響の伝播 | 中心に主題を置き周囲へ広げる。視線を中心に集め主題を強調 | 枝を増やすと中心が埋もれる |
| 相関図 | 網状のつながり・関係全体 | ビジネスモデル等、要素間の関係を一枚で俯瞰 | 「結局何が言いたい」となりやすい。斜め線のクモの巣になりやすい（3-8-2参照）。結論の一言・注釈を添える |
| マトリクス（2×2） | 2軸での分類・ポジショニング | 象限で位置づけ、空き象限や自社の位置を示す | 単純化しすぎ・細部が描けない点に注意 |
| ベン図 | 重なり・共通部分 | 2〜3集合の重なりに意味を持たせて強調 | イメージ先行になりやすい。重なりを色分けして意味を明示 |
| 数式型 | 掛け合わせ・加算・等式 | A＋B＝C や A×B＝C を要素の箱と演算子で表す | 本物の数値がなくても関係は伝わる。飾りすぎない |
| グループ図（少） | 中心＋周辺の集合 | 核となる要素の周りに関連要素を配置 | 放射との違いは「線でつなぐより囲い・近接でまとめる」点 |
| グループ図（多） | 多数要素の分類整理 | ロゴ・項目を群に分けて整然と並べる | 並べ方・区切りを工夫しないとごちゃつく |
| 項目比較図 | 自社 vs 他 の優位 | 比較軸ごとに並べ、自社の強みを打ち出す | 比較ポイント（どこが違うか）を強調。他は無彩色・自社だけ有彩色 |
| 規模比較図 | 量・規模の差（円の大小） | 円の面積差でインパクトを出す | 面積は誤読されやすい。数値を必ず併記 |
| 規模分析（TAM-SAM-SOM） | 包含・入れ子 | 大きな市場の中に取りに行く範囲を同心円で示す | 各円に数値ラベルを添える |
| 階層・レイヤー | 積層・土台ポジション | 何の基盤の上に成り立つかを層で示す | 立体表現は難易度が高い。原則フラットな帯の積層で表す |
| トライアングル | 3要素の均衡・相互補完 | 3つの価値が支え合う関係を三角配置で | 3要素限定。増やすなら別の型へ |
| 階段・ステップ | 段階的な到達・レベル | 段差をつけて「何段登るか」を感覚的に見せる | 昇る向き（左下→右上）を一定に |
| ガントチャート | 日程・期間・進捗 | プロジェクトの工程と期間を時間軸で | 期間バーは同じ時間グリッドに乗せる |
| 箇条書き（縦/横/列挙） | 単純な並列（関係が薄い） | 関係を持たない列挙。横並びは項目少なめ向き | これは厳密には図解でない。関係がないものを無理に図化しない |

#### 3-8-2. HTML/SVG 実装パターン（Chart.jsで描けないものの作り方）

**共通の実装方針**
- **箱は `div`、つなぎ（矢印・線）は SVG で描く。** ノードを絶対配置してSVGの `<line>`/`<path>` で結ぶか、フロー程度なら flex/grid で箱を並べ、間に矢印だけを置く。矢印頭は SVG の `<marker>` か CSS三角形（`border` トリック）で作る。
- **つなぎ線は原則タテ／ヨコの直交ルートにする（斜め線を使わない）。** 箱と箱を直接ナナメに結ぶと、線が箱の角に刺さって「ズレて見え」、素人っぽくなる。高さ・列がずれているときは L字／コの字のエルボー（`<path d="M.. H.. V.. H..">`）で直角に曲げて回す。斜め線を使ってよいのはサイクル・放射・散布など幾何的に必要な図だけ。
- **線はノードの中心でなく、相手に面した辺の一点（辺の中点など）に接続する。** 中心座標に引くと線端が箱に潜り込み、複数線が角へ集中してズレて見える。左のノードなら右辺、上のノードなら下辺、というように接続点を辺にそろえる。
- **関係線には矢印で向きを付け、ラベルは線の直線区間に沿って置く。** 双方向なら短いラベルを2つ、または両端に矢印。ラベルが線や箱に重なるなら、線区間の外側（上/下/脇の余白）へ逃がすか、下地に背景色の矩形を敷く。
- **ノードはきっちり列・行にそろえる。** 相関図・フロー・ツリーは、左列/中央/右列や等間隔の行にグリッドで整列させる。バラバラの座標に置くと直交ルートが引けず崩れる。
- **配置は可能な限り grid/flex で決め打ちし、絶対配置は最小限に。** 円環・放射・散布など幾何配置が必要なものだけ `transform: rotate()/translate()` や絶対座標を使う。
- **座標系を1つに固定。** SVGで線を引く図は、ノードも同じ SVG 内（`<rect>`＋`<text>`）に置くか、SVGを重ねる親に対する同一基準で置き、線とノードがズレないようにする。ノードもSVGで描くと接続点の座標を正確に合わせられて崩れにくい。
- **サイズ・間隔・色を統一。** 同レベルのノードは同じ幅・高さ・角丸・フォントサイズにする。バラバラだと素人っぽくなる。
- **clip-path で幾何形状（三角・台形・六角）を作るときは、隣り合う辺の座標を一致させて隙間なくタイルする。** 形どうしの幅・高さ・間隔を不用意に変えると全体の輪郭が崩れる（ピラミッド・パズルの注意点）。

**デザインを安定させる共通ルール（意図）**
- **主役を1つだけ差し色で強調し、脇役は無彩色/淡色にする。** 項目比較の自社、放射・相関の中心ハブ、ベン図の重なり、ステップの現在地など、注目させたい1要素だけ差し色で塗り、他は淡いトーンに落とす。全部に色を付けない。
- **色は意味に割り当てる。** 「重なり」「担当ゾーン」「役割の別」「前後の別」など、色分けには必ず理由を持たせる。飾りで色を増やさない。
- **読み解きの補助を1つ添える（多くて1つ）。** 相関図・マトリクスなど情報量の多い図には、結論の一言かキー注釈を短く置く。ただし図を実況しない（下記）。
- **フラット厳守（§3-6、デフォルト時）。** レイヤー/ピラミッドも 3D・影・グラデを使わず、ベタ塗り色面の重なり・濃淡で立体感を出す。参照デザインが角丸やソフトシャドウを持つ場合はそれに合わせる。
- **図を文章で実況しない。** 「〜の中に〜が入り…」と図を見れば分かることを本文でなぞらない。図の読み方を説明するキャプション（自分の図のエンコード解説）も書かない。
- **対等でない関係を対等な横並びカードで並べない。** 階層・包含・別カテゴリなら、横並び3カードで済ませず型で関係を示す。横並びカードは実質「箇条書き」。

**型別の作り方**

- **フロー（横/縦）・ステップ**：`flex`（横）/縦積みで等幅の箱を並べ、箱の間に矢印を置く。段や分岐で高さがずれる箇所は直交ルート（コの字）でつなぐ。番号バッジは円（`rounded-full`）。担当が分かれるなら背景色の帯（ゾーン）＋ラベルで「誰がどこまで」を示す。階段型は各箱に段階的な `margin-top`／高さを付けて段差を作り、昇る向きを一定にする。
- **サイクル**：要素を円周上に等間隔配置（親を `relative`、各ノードを `absolute` ＋ `transform: rotate(θ) translate(r) rotate(-θ)`）。ノード間は SVG の円弧パス（`<path d="M..A..">`）＋矢印マーカーでつなぐ。中心にテーマ名。
- **放射 / グループ（少）**：中心ノードを置き、周囲へ SVG の直線で結ぶ（放射＝ここは斜め可）か、囲み・近接でまとめる（グループ）。中心を差し色で強調。
- **相関図**：ノードを**きっちり列・行にそろえて**配置し（左列・中央ハブ・右列、あるいは上下＋左右）、中央に主役のハブ箱（サブ項目を内包してもよい）を置く。関係線は**直交ルート（タテ/ヨコ、必要ならL字・コの字）＋矢印**で、各ノードの辺と辺を結び、線ごとに短い交換ラベルを載せる。**ハブから四方へ斜め線を散らす“クモの巣”配置にしない**（これがズレて見える主因）。役割ごとにノードの色（ドット・上罫など）を分け、全体の下に結論の一行を添える。
- **同心円・包含（TAM-SAM-SOM、入れ子）**：`rounded-full` の div を入れ子にする（外＝淡色、内＝濃色）か、SVGの同心 `<circle>`。各層に数値ラベル。中心を合わせるため、絶対配置なら各円を `left:50%;top:計算値;transform:translateX(-50%)` で縦中心をそろえる。
- **ベン図**：`rounded-full` の円を2〜3枚、半透明のパレット色（`bg-slate/40` 等）で重ねる。重なり部分に共通概念のラベルを中央配置し、そこだけ色を強める。
- **ピラミッド**：**3段とも同じ幅・同じ高さの帯を `gap` なしで縦に積み**、各帯を `clip-path: polygon()` で切って上下の辺をぴったり接続する。頂点の帯＝三角 `polygon(50% 0,66.7% 100%,33.3% 100%)`、中段＝台形 `polygon(33.3% 0,66.7% 0,83.3% 100%,16.7% 100%)`、下段＝台形 `polygon(16.7% 0,83.3% 0,100% 100%,0 100%)`（上の帯の下辺＝次の帯の上辺になるよう％を合わせる）。段ごとに幅や段間gapを変えると全体が三角にならず崩れる。頂点の帯は狭いので文字を下側に寄せる（`flex items-end justify-center`）。
- **トライアングル**：3ノードを三角形の頂点に置き、SVGの辺で結ぶ（中心にテーマ）。
- **階層・レイヤー**：全幅の帯を縦に積む（下＝土台、上＝応用）。立体にせず、色の濃淡で層の別を出す。各帯にラベルと役割の短い注記。
- **マトリクス（2×2）**：`grid grid-cols-2 grid-rows-2`、または座標をSVGで固定（軸線・外枠・点・矢印・ラベルを1つのSVGにまとめると崩れにくい）。外側に縦軸・横軸ラベル。象限に要素、位置づけは点で打ち、現在地→めざす姿のような移動は矢印で示す。主役（自社・めざす姿）だけ差し色。
- **項目比較 / ビフォーアフター**：左右（または上下）に同じ行構造で対置。比較行のラベルを中央列に。自社/TO-BE 側だけ有彩色、相手/AS-IS 側は無彩色にしてコントラストで強調。
- **規模比較（円の大小）**：面積で差を見せる `rounded-full` の円。**必ず数値を併記**して誤読を防ぐ。
- **数式型**：要素の箱を演算子（＋ − × ＝）でつなぐ。演算子は大きめのテキスト。数値がなくても関係は伝わる。飾らない。
- **パズル / ハニカム**：六角形は `clip-path: polygon(25% 0,75% 0,100% 50%,75% 100%,25% 100%,0 50%)`。隣どうしを噛み合わせるときは負のマージン（`-ml-*`）で辺を重ね、全ピース同サイズにする。
- **グループ図（多）**：`grid` で群に区切り、群ごとに見出し帯。要素（ロゴ等）は同サイズ・等間隔で整列。
- **ガントチャート**：`grid` で左に工程名列、上に時間軸（等間隔の列）。期間バーは同じ時間グリッドに乗せた `div`（`grid-column` の start/end で開始〜終了列を span）。縦のガイド線は `background-image: linear-gradient(to right, 罫線色 1px, transparent 1px); background-size: 10% 100%` などで引く。
- **表**：`ul/ol/li` は使わないが、`table` またはグリッドで組んでよい。ヘッダー行を差し色、ゼブラは淡色で薄く。
- **地図・マップ**：純HTMLでは地図の下絵が作れないため、**ベースの地図SVG（簡略な日本地図/世界地図）か画像**を1枚だけ使ってよい（この型に限り外部素材可）。その上にピン（`absolute` の小円）を置き、引き出し線は短く整理する。素材が用意できないときは、地図に固執せず拠点一覧＋区分など別の型に切り替える。

#### 3-8-3. 実装後の自己チェック

- 選んだ型が「示したい関係」と一致しているか（列挙を無理に図化していないか）
- 箱＝div／つなぎ＝SVGで、線とノードがズレていないか
- **つなぎ線がタテ/ヨコの直交ルートで、ノードの辺に接続し、矢印で向きが付いているか（斜めのクモの巣になっていないか）**
- ノードが列・行にそろっているか
- **clip-path の図（ピラミッド・パズル・台形）で、隣の辺の座標が一致して隙間なくタイルされ、全体の輪郭が崩れていないか**
- 同レベルのノードのサイズ・間隔・色が揃っているか
- 差し色は主役1つに絞れているか（全部に色を付けていないか）
- フラット（デフォルト時：影・グラデ・3Dなし、直角）か、参照デザインの装飾ルールに合っているか
- 図を実況する文・図の読み方解説を本文に書いていないか
- 情報量の多い図に、結論の一言または注釈が1つ添えてあるか
